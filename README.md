# SortNStock

A client-side Minecraft Fabric mod for **inventory sorting** and **automatic restocking**, with
optional **Litematica** schematic and **QuickShulker** integration.

SortNStock is deliberately conservative about what it does:

- **Client-only.** Nothing is required on the server.
- **It never creates items.** No spawning, duplicating or "refilling". Every single movement is
  an ordinary container click (`ContainerInput.PICKUP` / `SWAP`), so the server validates each
  action exactly as if you had clicked it yourself.
- **It never places blocks, never builds and never modifies a schematic.** Sorting out the
  placement is Litematica's job; SortNStock only puts the required item into a hotbar slot.

> **Status: no gameplay testing has been performed by the developer.**
> The project compiles, its dependencies resolve and its configuration is validated, but every
> in-game behaviour is **pending user verification**. See `docs/USER-TEST-CHECKLIST.md`.
> No result in this repository should be read as "tested in game".

### Why Java 25 and not 21

Minecraft 26.1 moved to **Java 25**, and 26.1 is also the first **unobfuscated** Minecraft
release. Consequences that shaped this project's build:

- The Gradle JVM must be Java 25 (`gradle.properties` pins `org.gradle.java.home`).
- There are **no mappings** — Yarn is no longer supported, and the build uses Mojang's official
  names directly. `build.gradle` therefore declares no `mappings` and uses the non-remapping
  `net.fabricmc.fabric-loom` plugin.
- `modImplementation` / `modCompileOnly` are replaced by plain `implementation` / `compileOnly`,
  and `remapJar` by `jar`.

Reference: [Fabric for Minecraft 26.1](https://fabricmc.net/2026/03/14/261.html).

If your Java 25 install lives somewhere else, either edit `org.gradle.java.home` in
`gradle.properties` or delete that line and point `JAVA_HOME` at Java 25.

## 2. Building

```bash
# Java 25 must be the Gradle JVM (see above)
./gradlew build
```

The mod jar is written to `build/libs/sortnstock-26.1.2-<version>.jar`.

Install it alongside MaLiLib in your `mods/` folder; add Litematica and/or QuickShulker if you
want those integrations.

### Building and installing into the test instance

```
pwsh -File tools\build-and-install.ps1
```

This builds, refuses to install if the build or any test failed, copies the jar into
`<test-instance>\.minecraft\mods\`, and prints the jar hash and timestamp. It also
warns if Minecraft is currently running — **a jar replaced while the game is running is not
loaded**, so the game has to be restarted for a new build to take effect. This is the only
supported way to install a build; see `AGENTS.md` for the standing rules.

### Notes for this machine

The JDK trust store on the development machine did not validate the public TLS chain used by the
Gradle/Maven endpoints, which broke dependency downloads with `PKIX path building failed`.
`gradle.properties` therefore sets `-Djavax.net.ssl.trustStoreType=WINDOWS-ROOT` so the JVM can
use the Windows trust store. If your JDK trusts the public CAs normally, remove that flag.

## 3. Using it

### Hotkeys (defaults)

| Hotkey | Default | Action |
|---|---|---|
| Sort container | **Middle mouse** | Sort the container under the mouse cursor |
| Open config GUI | **`T` then `K`** | Open the SortNStock config screen |

These are the only two hotkeys. The restock module is switched on and off from the config screen;
earlier versions also had (unbound) keys for "restock now", "toggle restocking" and "toggle the
Litematica integration", which were removed on request. Because they were unbound by default,
nothing changes for anyone who never set them.

Both hotkeys use `Context.ANY`, so they also work while a screen is open — which sorting requires.

Note that middle mouse is **also vanilla's "pick block" button**, so both actions fire on the same
click. Rebind it in the config GUI if that is a problem for you.

The config screen is generated by MaLiLib. It can be opened three ways: the `T` then `K` hotkey,
the config button in **Mod Menu**, or MaLiLib's own mod list / config switcher (`SortNStock` entry).

Mod Menu support is a small `modmenu` entry point (`com.sortnstock.compat.modmenu.ModMenuImpl`).
It has to exist because Mod Menu only auto-detects Cloth Config's AutoConfig — it knows nothing
about MaLiLib, and MaLiLib's own Mod Menu entry provides a screen for MaLiLib rather than for the
mods using it. Litematica ships an identical class. Mod Menu is a `compileOnly` dependency: it is
the only thing that asks Fabric Loader for that entry point, so without Mod Menu the class is never
loaded and nothing is required at runtime.

### Sorting

Sorting needs no key-modifier and no container setup: hover a slot and press the sort hotkey.
SortNStock works out *which* inventory you mean from the slot under the cursor:

- hovering a chest slot sorts that chest,
- hovering your own inventory sorts **your 27 main inventory slots only**.

The **hotbar is never sorted**, and neither are the armor slots or the offhand slot. This is fixed
behaviour with no option behind it: the hotbar is a hand-arranged quick-access bar, and a sort
silently rearranging it — or moving the tool you are holding — is not something worth making
configurable. It also means hovering any part of your inventory, hotbar included, targets the same
27 slots.

Supported sort keys: registry name, display name, count, durability, NBT/components, tags.
Sorted ascending, with optional merging of stacks and compaction of items forwards. There is no
sort-direction option: every sort is ascending.

Two ordering rules are fixed rather than configurable:

- **Shulker boxes are placed in the last slots of the container**, whichever key and direction are
  used. They are reserved into a tail block at the end of the region; ordinary items are packed at
  the front and the slots in between are left empty. With 27 slots, 12 ordinary stacks and 9 boxes,
  the boxes occupy slots 18-26 and slots 12-17 form the gap. A container too full for a gap simply
  becomes contiguous, with the boxes still last.
- **In creative mode the middle mouse button belongs to vanilla.** Where the sort hotkey is bound to
  the middle mouse, sorting steps aside on a non-empty slot so clone / pick-block works. On an
  empty slot there is nothing for vanilla to clone, so sorting still runs — which keeps it reachable
  in creative. Rebinding the sort key removes the restriction.

A vanilla GUI button click plays when a sort starts, so the hotkey gives audible feedback instead
of appearing to do nothing.

Sorting makes **partial progress rather than all-or-nothing**: a pair of slots that cannot be
reordered with the available click primitives is skipped (and counted), while everything else is
still sorted. Skipping never touches the inventory, so it carries no item-loss risk.

The whole click program is dispatched **within a single client tick**, with no per-tick cap. A plan
is computed from a client-side snapshot of the container, so executing it entirely inside one tick
means that snapshot cannot go stale mid-plan — there is no window in which an interleaved server
slot correction, a manual click or a container close could invalidate the remaining operations.
This is the same basic approach client-side inventory mods use. The trade-off is a burst of
container-click packets, which is discussed under known limitations.

### Restocking

Restocking keeps your **hotbar and/or offhand** stocked with the items you already carry.

```
threshold = restockMinCount
target(item) = one full stack of that item (64 for most, 16 for eggs/snowballs, …)
```

An item is topped up once its amount in the target slots falls to or below the threshold, and it is
then filled **straight to one full stack**. There is no hysteresis setting: the item itself defines
how big a stack is, so a second number would only raise the question of how the two should
interact.

`restockMinCount` is adjustable from **0 to 64**. At `0` the rule becomes "top up only once the slot
is empty", which is a useful mode: place blocks until the stack runs out and the next placement
refills it to a full stack. Because an empty slot no longer says what used to be in it, the trigger
remembers the item that was consumed on the previous tick so it can still be identified.

Items that do not stack (stack size 1, such as tools) are deliberately excluded from count-based
restocking.

**The only trigger is the held item's count decreasing**, and it is not configurable. A check runs
when the stack in the main hand gets smaller, which covers using or consuming an item (eating,
throwing, drinking) and placing a block. The periodic-tick, after-pickup and after-container-open
triggers were removed on request, so restocking is driven purely by actually consuming something
from the hand rather than polling on a timer. With one trigger left there is no trigger-selection
option at all — `restockEnabled` is the master switch. Cooldown and a per-tick operation cap
provide the throttling.

The same principle applies to the Litematica integration: its former `litematicaTriggerTiming`
option (right-click / held-count-change / periodic tick) is gone. The right-click hook is the one
fixed evaluation point, because it is the only moment a restock can land before the slot switch.

Sources are tried in a configurable priority order: **player inventory → carried shulker boxes →
open container**. The player inventory and the open container are always available; only the carried
shulker boxes can be switched off, and that lives in the shulker-box config section and GUI tab.

### Litematica integration

With Litematica installed and the integration enabled, SortNStock hooks in at exactly one point —
the head of Litematica's `InventoryUtils.schematicWorldPickBlock` — which is the first moment that
is both after Litematica has decided a block should be placed and before it switches the hotbar
slot. There is no trigger-timing option: this single point is the whole integration.

The ordering for a single right-click is:

```
SortNStock restock clicks  →  Litematica pick block (slot switch)  →  Easy Place (block placed)
```

Because the clicks are dispatched synchronously inside that tick, the **same** right-click can use
the restocked stack — no second click is required for the client-side hand check. (Whether the
*server* also accepts the whole click chain in one tick is a runtime property that has not been
verified; see the "known limitations" and the test checklist.)

SortNStock does **not** switch slots (Litematica's pick block does), does **not** place blocks
(Easy Place does), does **not** intercept or cancel the right-click, and does **not** modify the
schematic.

## 5. Known limitations and deliberate design decisions

1. **Litematica's option is called `pickBlockableSlots`, not `PICK_BLOCK_USABLE_SLOTS`.**
   The design brief referred to a `PICK_BLOCK_USABLE_SLOTS` option. No such option exists in
   Litematica 0.27.14. The real option is `Configs.Generic.PICK_BLOCKABLE_SLOTS`, a
   comma-separated list of **1-based** hotbar slot numbers defaulting to `"1,2,3,4,5"`.
   SortNStock re-parses that same string (Litematica keeps its parsed list private) so Litematica's
   config remains the single source of truth. There is deliberately **no** SortNStock slot list,
   **no** blacklist and **no** fallback — if the list is empty, the restock is skipped.

2. **Same-item reordering needs an empty hotbar slot.** A cursor-based swap relies on vanilla
   behaviour: left-clicking two slots with different items swaps them, but with the *same* item it
   merges instead. When a sort needs to reorder two slots holding the same item with different
   counts, SortNStock switches to a hotbar-scratch swap. If no usable empty hotbar slot exists
   (e.g. a full hotbar while sorting a full inventory), that **pair is skipped** and counted, and
   the rest of the sort still happens. Skipping never modifies the inventory, so it carries no
   item-loss risk — the arrangement is simply left partially sorted rather than not sorted at all.

   > This changed in response to user feedback: the earlier behaviour aborted the *entire* sort
   > when a single pair could not be swapped, which made sorting appear to do nothing at all on a
   > nearly-full inventory.

3. **Sorting sends its whole click program in one tick, with no throttle.** A sort is dispatched as
   a burst of ordinary container-click packets inside a single client tick — there is deliberately
   no per-tick cap. This was chosen because a plan is computed from a client snapshot, and
   finishing inside one tick removes any window in which a server slot correction, a manual click
   or a container close could invalidate the rest of the plan.

   The cost is the burst itself: a large sort can emit several dozen clicks at once. On a server
   with packet-rate limiting or anti-cheat, that is the one place SortNStock is aggressive. Note
   the deliberate asymmetry — the restock module *is* throttled (`restockMaxOpsPerTick`, default
   1 per tick), while sorting is not.

   Items cannot be destroyed either way, since every click is an ordinary operation the server
   validates. But if a server rejects one click mid-batch, the remaining clicks were computed
   against the client's prediction, so the final arrangement can come out scrambled and an item may
   be left on the cursor.

   > **待用户验证** — behaviour on a rate-limiting or anti-cheat server has not been tested. See
   > the test checklist.

4. **Fixed: sorting could hang the game, and the results were not what a "tidy up" should give.**
   Four defects reported from in-game testing have been corrected:

   - **Freeze.** The merge phase could loop forever. When two same-item stacks overflowed one full
     stack, the code refilled one stack to the cap and pushed the remainder back to the other —
     but if that stack was *already* at the cap this changed nothing, while the loop still treated
     it as progress. The client thread spun in `mergePhase` before a single click was sent, so the
     symptom was "nothing sorted *and* the game froze". The merge now only counts as progress when
     a stack actually grows, and the loop additionally has a hard safety bound that emits a partial
     plan and logs an error rather than hanging.
   - **Armor and offhand slots were swept into the player inventory region.** The armor slots
     (container slots 36-39) and the offhand slot (40) are backed by the *same* `Inventory`
     instance as the main inventory, so grouping by container identity caught them too. Worse,
     `maxStackSize` asked the region's first slot, which was the helmet slot with a limit of 1, so
     every item looked unstackable and merging silently did nothing. The region is now restricted
     to the 36 real inventory slots, and the stack limit is taken across the region instead of
     trusting one arbitrary slot.
   - **Stacks were never filled.** The merge decided whether to act by comparing the *number* of
     stacks of an item against the target's. Two stacks of 50 and 60 have the same stack count as
     the ideal 64 + 46, so nothing was merged and both stayed half full. Merging is now fixed behaviour (it used to be the `sortMergeStacks` option) and fills greedily until no stack has room; maximal filling
     yields a unique set of counts, so this lands exactly on the ideal.
   - **Items were not packed forwards.** The option controlling this was `sortKeepEmptySlots`,
     which defaulted to *on* — "leave the empty slots alone and only reorder in place" — so a
     sorted container still looked scattered. Flipping that default was not enough: **a persisted
     config value always overrides a code default**, so every existing `config/sortnstock.json`
     kept behaving as before. The option was therefore renamed to `sortCompactItems` and defaulted to *on*; it has since been removed entirely, so compaction is always applied now. The stale key is dropped when the config is next saved.

   > All four fixes are **待用户验证** — they are reasoned from the code and confirmed to compile,
   > not observed in game.

5. **Moving items out of a shulker box needs QuickShulker.** Shulker *contents can be read* with
   pure vanilla data components (`DataComponents.CONTAINER`, via MaLiLib), so reading works with or
   without QuickShulker. But changing a shulker's contents is server-authoritative, so the box must
   be opened first. That is a two-phase flow: SortNStock asks QuickShulker to open a box containing
   the wanted item, and the actual move happens on a later pass once the box is open. Without
   QuickShulker this two-phase flow does not exist, so a carried box can only be used as a source
   once you open it yourself.

6. **QuickShulker's 26.1 artifact declares no Minecraft version constraint.** It is a `recommends`
   and everything touching it is runtime-guarded, but it was built for the 26.1 line rather than
   specifically 26.1.2.

7. **The Mixin is version-coupled to Litematica.** It targets one exact method signature of
   Litematica **0.27.14** (LTS/26.1 branch, commit `edf9ced2af2244d56fc20086883a014bf051b1b8`).
   A future Litematica release may move or rename that method and the injection would fail to
   apply. The integration is also hard-gated on Litematica being present — the mixin config uses a
   plugin that skips the mixin entirely when Litematica is absent, so a vanilla-plus-SortNStock
   install cannot crash on a missing target class.

8. **The sort hotkey defaults to middle mouse, which is also vanilla's pick block.** Both actions
   fire on the same click. This is the requested default; rebind it in the config GUI if the
   overlap is a problem. Note that when a sort *does* start, SortNStock suppresses the vanilla
   action for that click; if the sort declines to run (already sorted, nothing safe to move),
   vanilla's pick block goes through as normal.

9. **Shared client-side caveat.** SortNStock changes the inventory by sending normal container
   clicks. A modded server that rejects or rate-limits inventory clicks may disagree with the
   client, and Litematica's own `easyPlaceSwapInterval` / "easy place is too fast" logic exists for
   precisely that reason. On such servers a restock may not take effect for the triggering click.
